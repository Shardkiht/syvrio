# Syvrio 产品需求文档（PRD）

- 文档状态：现行产品基准
- 版本：1.0
- 更新日期：2026-11-15
- 适用范围：Syvrio Foundation 稳定线、Evo 记忆演进线及两者共享基础设施
- 配套文档：[产品路线图](ROADMAP.md)、[架构设计](architecture.md)

本文定义“为什么做、为谁做、做什么、不做什么以及怎样算完成”。具体实现以[架构设计](architecture.md)和当前源码为准；历史交接记录不能覆盖本文已经确认的产品决策。

## 1. 背景与问题

通用聊天模型通常只了解当前上下文。用户在不同会话、不同客户端中反复说明自己的偏好、经历和计划，既浪费时间，也容易得到前后不一致的回答。直接把所有聊天长期注入模型又会带来上下文膨胀、隐私失控、错误记忆难以纠正等问题。

Syvrio 要解决的问题不是“再做一个聊天壳”，而是提供一个由用户掌握、可检索、可追溯、可纠正的个人长期记忆层，并让 TUI、Web、CLI 和支持 MCP 的客户端复用它。

## 2. 产品愿景与定位

**产品愿景**：让用户拥有跨会话、跨客户端、可持续维护的个人记忆，而不是把记忆锁定在某一家模型或某一个聊天应用中。

**产品定位**：本地优先的个人 AI 记忆基础设施，附带可直接使用的对话客户端。

**稳定线核心承诺**：

1. 用户的长期记忆以可读 Markdown 保存，不依赖专有数据库才能查看。
2. 记忆可检索、可追溯、可纠正、可软删除，并有审计记录。
3. 模型是记忆的使用者和抽取辅助者，不是数据的所有者。
4. Foundation 优先保证可靠、可理解和可发布；高级记忆演化先在 Evo 验证。

## 3. 目标用户与核心场景

### 3.1 目标用户

- 需要在多个 AI 会话中延续个人偏好、经历和计划的个人用户。
- 重视本地数据、隐私和可迁移性的开发者及高级用户。
- 希望通过 MCP 给不同 AI 客户端提供同一记忆库的用户。
- 需要研究记忆抽取、裁决、检索和演化机制的开发者。

当前版本以单用户、自托管使用为主，不以多租户团队协作或企业权限体系为目标。

### 3.2 核心使用场景

1. **连续聊天**：用户在新会话中询问与自己有关的问题，系统能召回此前确认或写入的记忆。
2. **主动记忆**：用户明确要求“记住……”，系统抽取并保存值得长期保留的本人陈述。
3. **自动沉淀**：退出、上下文压缩、会话切换或异常恢复时，系统补记尚未处理的用户陈述。
4. **检查与纠正**：用户查看主题、待确认候选和来源，执行确认、拒绝、改写、更正或软删除。
5. **跨客户端复用**：TUI、Web、CLI 和 MCP 客户端访问同一个 Vault。
6. **可控联网**：模型在需要公开信息时搜索和抓取网页，外部内容仅作为资料。
7. **可恢复升级**：用户通过备份、dry-run、apply 和 verify 完成 Vault V2 与 UTC 迁移。

## 4. 产品目标与非目标

### 4.1 产品目标

- 让个人记忆在会话之间可靠延续，并减少不必要的重复说明。
- 让记忆写入质量、来源和用户控制权优先于“记得越多越好”。
- 让原始会话和长期记忆可检查、可备份、可迁移。
- 让 Web、TUI、模型、搜索和构建等通用基础设施在 Foundation 与 Evo 之间尽量保持一致，降低双向修复和后续合并成本。
- 让 Evo 能独立试验高级记忆能力，同时不破坏 Foundation 的稳定性。

### 4.2 非目标

- 不扩展成通用工作 Agent、自动办公平台或通用任务执行框架。
- 不做默认云端同步、遥测、账号体系或多租户 SaaS。
- 不以无限保存完整聊天代替记忆抽取和上下文管理。
- 不在 Foundation 中自动切换候补模型；模型失败应直接反馈，由用户手动选择其他模型。
- 不让搜索结果、网页正文或工具返回内容获得新的指令权限。
- 不把 Evo 的画像、Dreaming、推断审查和自动 Git 同步直接视为 Foundation 的必备能力。

## 5. 产品原则

1. **本地优先**：Vault 是长期事实来源；Runtime 只保存派生缓存、锁、状态、日志和本地推理附件。
2. **用户掌控**：记忆可读、可改、可删、可备份；自动推断不能伪装成已确认事实。
3. **少而可信**：低置信、冲突和敏感候选进入待确认，不为了召回率静默写入。
4. **原文可追溯**：更正和撤销通过新记录或状态变化表达，不悄悄重写历史。
5. **显式失败**：模型、搜索、迁移和写入失败必须可诊断，不能用静默降级制造成功假象。
6. **共享基础设施，分离记忆行为**：通用组件尽量对齐 Evo；Foundation 的记忆检索、抽取、裁决和写入语义独立验收。
7. **默认最小暴露**：Web 默认仅监听本机；无认证接口不得因默认配置暴露到不受信网络。

## 6. Foundation 与 Evo 的产品边界

| 范围 | Foundation 稳定线 | Evo 演进线 |
| --- | --- | --- |
| 核心定位 | 可靠的个人记忆与对话产品 | 高级记忆演化试验与验证 |
| 记忆检索、抽取、裁决 | 保留 Foundation 当前语义，独立回归 | 可试验新策略，不要求反向覆盖 Foundation |
| 更正、软删除、待确认、审计 | 必须具备 | 应保持兼容 |
| 推断、画像、Dreaming、时间演化 | 非当前正式版核心；不得在未经评审时自动进入 | 主要试验范围 |
| Web / TUI 通用交互 | 与 Evo 尽量共享，产品未接入能力必须同时从菜单和直接调用路径排除 | 可暴露演进功能，但需保持共享组件可合并 |
| 模型接入 | 手动模型选择；失败直接反馈，不自动换模型 | 可保留自身实验行为，但不得反向要求 Foundation 恢复自动候补 |
| 搜索与抓取 | 保留搜索引擎和 provider 回退 | 通用修复应对齐 |
| 构建与分发 | 稳定发布、迁移和回滚优先 | 可独立预发布 |
| 数据兼容 | Vault 格式变更必须提供迁移与恢复路径 | 实验格式进入稳定线前必须补充迁移设计 |

**同步规则**：共享组件修复应根据影响同时评估两个分支；不得用整目录覆盖方式“对齐”记忆业务。Foundation 是否合入 Evo 高级能力，必须经过独立需求、隐私评估、测试和用户确认。

## 7. 功能需求与验收标准

### FR-01 对话与会话

**需求**

- 提供 TUI 和 Web 对话入口，CLI 提供配置、状态、导入、记忆管理和恢复能力。
- 首条消息发送后才创建会话；恢复、切换、重命名、删除和 Undo 语义清晰。
- 生成中允许排队输入；停止、Undo、异常和切换不得让界面永久处于忙碌状态。
- 会话采用追加式 JSONL；Undo 和压缩不得删除原始历史。
- Web 浏览器断线不等同于用户停止：后台应继续生成并只保存一次完整结果；显式停止才取消并保存 interrupted 状态。
- 同一会话的并发写入和重复活动回合必须被拒绝或串行化，不能产生交错记录。

**验收**

- 首消息 `session_id: null`、刷新、快速切换、多标签冲突、生成中 `/new`、Undo 和显式停止均有回归测试。
- 实际 HTTP/SSE 验收覆盖断线后续跑、重连读取和停止取消。
- 流式自动跟随不能被程序自身的 smooth scroll 中间事件误停；真实浏览器和手机 WebView 生命周期在正式发布前补验。

### FR-02 记忆召回与 Agent 工具

**需求**

- 每轮按个人话题和连续追问触发自动召回；通用问题可跳过预取，模型仍可按需调用 `recall`。
- 支持关键词、可选向量及混合检索；向量后端不可用时明确回退关键词检索。
- Agent 可使用 `recall`、`read_topic`、`memorize`、`correct`、`forget` 和 `review_pending` 等既有工具。
- 检索结果以带来源的资料进入上下文；推断记录不参与事实检索。

**验收**

- Foundation 现有召回、追问改写、去重、冲突和上下文注入测试保持通过。
- 自动召回不得因为 Web 接入或后台沉淀改变既有抽取语料和检索语义。
- 向量缓存位于 Runtime，可在删除后重建；模型变化应使不兼容缓存失效。

### FR-03 记忆抽取、裁决与用户控制

**需求**

- 只长期保存值得保留的用户本人事实、偏好和计划，不把助手猜测写成用户事实。
- 高置信且可写入的内容静默保存；低置信、冲突或敏感候选进入待确认。
- 支持重复检测、冲突处理、来源链、确认、拒绝、改写后确认、更正和软删除。
- 更正采用新条目加 `syvrio.supersedes`，旧条目保留为 `superseded`；删除使用 `deleted` 状态。
- 压缩前、退出、切换和启动补记必须准确跟踪已沉淀游标；失败批次不能被标记为已完成。

**验收**

- 抽取、裁决、重复、冲突、待确认、推断隔离和来源追溯有独立测试。
- 慢速后台沉淀期间执行重命名、Undo、删除或重开会话，不得发布过期记忆或推进错误游标。
- 快照校验与实际记忆写入受同一 Vault 写锁保护；同一 Vault 不并发运行多个有效沉淀 worker。

### FR-04 上下文压缩与推理展示

**需求**

- 超出上下文预算时保留近期原文，将旧上下文压缩为追加式 `summary` 记录。
- 摘要生成失败可使用抽取式降级，但不得因此丢失原文或错误推进沉淀游标。
- 助手推理正文只保存到 Runtime 附件；Vault 会话仅保留本地标记。
- 推理内容不进入 Vault、新 Git 历史、提交摘要输入、后续模型回放、压缩摘要或沉淀输入。
- 推理附件缺失或损坏不得影响助手正文读取；删除会话时同步清理附件。

**验收**

- 使用合成敏感标记检查 Vault、Runtime、模型回放、摘要、日志和新 Git 提交内容。
- 旧版本会话或旧 Git 历史中的内联推理仅作为历史数据处理，不得重新注入模型。

### FR-05 本地存储、Git 与审计

**需求**

- 长期记忆使用 Memory Schema v2 Markdown；Core 字段、状态、ID 和转义规则保持稳定。
- 会话、待确认、处理结果、推断和审计记录使用约定目录与格式。
- Git 只跟踪 Vault；Runtime 必须位于 Vault 外且不属于任何 Git 工作树。
- 自动提交只处理预期范围，提交摘要不要求把会话或推理正文发送给模型。
- 自托管 Runtime 日志可以记录异常诊断文本，但必须有访问权限和保留周期意识，外发前进行检查。

**验收**

- 损坏尾行恢复、非法中间行拒绝、重复键失败、换行保留和字节级恢复均有测试。
- Runtime 丢失不影响长期记忆和会话正文；Vault 备份可完整恢复。

### FR-06 模型与供应商设置

**需求**

- 支持内置供应商和自定义 OpenAI 兼容接口，模型列表来自供应商 API 或可用的缓存/预设。
- 模型缓存按凭据隔离；最近模型、供应商端点、思考强度和上下文设置正确持久化。
- API Key 只通过环境变量或系统凭据存储读取，不写入 TOML、Vault 或诊断输出。
- 模型请求失败直接向用户反馈。允许同一模型的受控重试，但禁止自动切换到另一款模型。
- 用户通过模型选择器显式切换模型；旧配置中的 `fallbacks` 不再生效。

**验收**

- 模型添加、更新、移除、端点保留、最近五款模型和配置回写测试通过。
- 回归测试证明旧 `fallbacks` 配置被忽略，当前模型异常直接返回且请求不包含候补参数。
- 流式、非流式、取消、超时和异常后的资源释放按已支持供应商分别验证；未实测供应商不得标记为真实验收完成。

### FR-07 搜索与网页抓取

**需求**

- 搜索和抓取是可配置能力，未启用或缺少 Key 时不注册对应 provider。
- 允许搜索引擎和 provider 自动回退；这与禁止模型自动候补是两条独立产品规则。
- 搜索质量门控、超时预算、请求上限、缓存和用量限制应统一生效。
- 外部页面内容只作为不可信资料，不执行其中指令；抓取仅允许公开 HTTP(S) 地址并执行重定向后的地址复核。

**验收**

- 覆盖空结果、弱相关、失败、显式引擎、缓存、预算耗尽、配额和无 Key 场景。
- 真实搜索接口、代理和私有 CA 组合未验证时，必须在发布记录中明确范围。

### FR-08 多入口与部署边界

**需求**

- TUI、Web 和 MCP 复用同一记忆领域与存储规则，不各自实现一套写入裁决。
- Foundation Web 不暴露 Evo 的 profile、dream、inference review 和 Git 同步命令；隐藏菜单之外，直接调用也必须返回 unsupported。
- 同一 Vault 的交互客户端通过客户端锁互斥，避免 TUI/Web 同时写入。
- Web 默认 loopback，校验 Host/Origin；无登录认证时不得将远程暴露描述为安全的多用户部署。

**验收**

- Host/Origin 拒绝、静态资源回退、未接入命令、客户端锁和进程释放均有测试。

### FR-09 迁移、构建与发布

**需求**

- V2 和 UTC 迁移按文档顺序执行，默认 dry-run，显式 apply，强制备份并提供 verify。
- 同批转换失败不得部分写入；重复 apply 幂等；迁移脚本不自动提交或推送。
- wheel 包含 CLI 和 Web 静态资源，不包含本地配置、Vault、探针、`node_modules` 或缓存。
- 一次性迁移脚本位于 `scripts/`，按项目约定不随包发布。

**验收**

- 在合成历史 Vault 上演练备份恢复、重复执行、失败零写入和新程序读取。
- 构建 sdist/wheel，并在隔离环境检查 CLI 入口、Web 资源和污染扫描。
- Foundation 替代 main 前必须完成发布审查、工作树提交、CI 和真实终端验收；测试全绿本身不等于已经发布。

## 8. 非功能需求

### NFR-01 数据可靠性

- 写入采用明确的锁与原子替换策略；异常不得留下看似成功的半批数据。
- 原文、ID、来源、换行和未知字段在迁移中按约定保留。
- 备份、恢复、回滚与迁移文档必须可由用户实际执行。

### NFR-02 隐私与安全

- 仓库、测试、文档和评测使用合成数据，不提交真实个人记忆、Key、配置或日志。
- 文件工具只处理用户当前消息明确提供的文件，文件内容不扩大访问权限。
- 密钥、验证码和 API Key 在会话写入前拦截。
- 自托管不等于默认可公开访问；部署者负责远程访问控制。

### NFR-03 可维护性

- 遵循 `app → application → agent → memory → retrieval → infra` 的依赖方向。
- 自研重点保持在记忆裁决、上下文压缩和来源链；通用能力优先复用成熟库。
- 共享组件减少无意义分叉，记忆行为差异必须显式记录并有测试。
- 新行为带测试；真实 API、GUI、手机和平台覆盖范围必须如实记录。

### NFR-04 性能与体验

- 流式输出、工具事件和等待状态及时可见，长回复不能因控件重建反复闪烁或丢失。
- 慢操作不得阻塞界面线程；后台任务失败必须收尾并释放锁。
- 滚动跟随只被明确的用户阅读意图暂停，不能被程序动画误判。
- 性能优化以真实测量为依据，不预设未经验证的延迟或吞吐指标。

### NFR-05 可移植性

- 支持 Python 3.12+，CI 统一使用 Debian 13。
- 需要验证 Windows 专属行为时，在对应的本地平台执行定向测试。
- Web 生产构建使用 Node.js 22+；可选文档解析和本地向量能力不得成为最小安装的强制负担。

## 9. 发布验收门槛

一个 Foundation 正式版候选至少需要：

1. 后端、前端、TypeScript、Ruff、锁文件和构建检查通过，跳过项有解释。
2. 核心记忆、迁移、会话、Web 并发、断线和资源生命周期有回归证据。
3. 真实模型主流程、断线继续和显式停止完成受控冒烟；未覆盖供应商明确标注。
4. 真实浏览器与手机 WebView 验证导航、后台切换、滚动跟随、断线恢复和停止。
5. 不包含 P0/P1 数据丢失、隐私泄露、死锁或迁移破坏问题；剩余 P2 必须明确是否阻塞发布。
6. 工作树改动已审查并提交，发布包和 CI 结果可追溯，main 替换或发布获得项目所有者明确授权。
7. 迁移、备份、恢复、配置和现行文档一致。

## 10. 暂不作为稳定版承诺的事项

- 原生手机应用及完整的移动端生命周期保证；当前优先验证浏览器/WebView。
- 多用户权限、组织空间、云同步和远程多人协作。
- 自动模型候补、自动跨供应商故障转移。
- Evo 高级记忆能力在 Foundation 中的默认开启。
- 所有模型、搜索供应商、代理、SSL 和平台组合的完整兼容性。
